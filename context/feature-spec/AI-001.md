# AI-001 — Trigger.dev Setup

## A. Identity and Objective

- **Feature ID:** AI-001
- **Title:** Trigger.dev Setup
- **Primary objective:** Configure Trigger.dev in the Next.js project, set up the Trigger.dev environment variables, and create a no-op test task to verify the connection between the app, Trigger.dev, and the database.
- **Expected outcome:** The Trigger.dev CLI is installed, `trigger.config.ts` is configured at the project root, a test task runs successfully in the Trigger.dev dashboard (or local dev server), and the environment variables (including the database URL) are correctly synced.
- **References:** `planning/feature-map.md` AI-001; `context/architecture.md` Stack (Background Jobs), Data and Storage; `context/code-standards.md` Next.js, Data and Storage; `AGENTS.md`.

## C. Context and Dependencies

- **Prerequisites:** PROJ-005 complete and verified (the database is set up and Prisma is working).
- **Contract introduced:** The Trigger.dev configuration and the pattern for background jobs.
- **Contract consumed:** `prisma` from `lib/db.ts` (specifically for testing the pooling behavior mentioned in D.2).
- **Approved decisions:**
  - Trigger.dev v4 (or latest v3/v4) is used for background jobs.
  - **Prisma Connection Pooling:** The Next.js server and Trigger.dev tasks run in different environments. Trigger.dev tasks should use a Prisma client with a connection limit of `max: 1` to avoid exhausting Neon's connection pool during heavy background processing .
  - Do not import the Next.js `prisma` singleton directly into Trigger.dev tasks if it uses default pooling. For this setup unit, we will just verify a basic task runs. The specific `max: 1` client setup will be implemented in AI-002 when the actual graph generation task is created.
  - Trigger.dev must have access to both `DATABASE_URL_UNPOOLED` and `DATABASE_URL` to run Prisma queries with the configured pooling fallback.
  - Supply deployed task runtime variables through the Trigger.dev Dashboard's environment-variable settings for the target environment, not an environment-variable sync extension. The Prisma build extension generates/bundles Prisma Client; it does not provision runtime variables. Configure both `DATABASE_URL_UNPOOLED` and `DATABASE_URL` there as secret values, and verify their names are present in the target environment without displaying or logging their values.
  - Local development uses `npx trigger.dev@latest dev`, which runs the tasks locally and connects to the cloud dashboard.

## D. Implementation Requirements

### 1. Create `trigger.config.ts`

Create the configuration file at the root of your project.

START OF trigger.config.ts snippet

    import { defineConfig } from "@trigger.dev/sdk/v3";
    import { prismaExtension } from "@trigger.dev/build/extensions/prisma";

    export default defineConfig({
      project: process.env.TRIGGER_PROJECT_REF!,
      dirs: ["./trigger"],
      build: {
        extensions: [
          prismaExtension({
            schema: "prisma/schema.prisma",
          }),
        ],
      },
    });

END OF trigger.config.ts snippet

_(Note: If Trigger.dev v4 is installed instead of v3, change the SDK import from `/v3` to the standard import if applicable. The `prismaExtension` ensures Prisma Client is generated and bundled correctly for the Trigger.dev environment .)_

The `prismaExtension` does not sync environment variables. For deployed tasks, add `DATABASE_URL_UNPOOLED` and `DATABASE_URL` to the selected Trigger.dev Dashboard environment's variables; do not add an environment-variable sync extension or put either value in this configuration file. Before deployment, verify that both variable names are configured for that target environment without reading their values into logs or conversation.

### 2. Create a Test Task `trigger/test-task.ts`

Create a simple task that logs a message and queries the database to prove the connection works.

START OF trigger/test-task.ts snippet

    import { task } from "@trigger.dev/sdk/v3";
    import { PrismaClient } from "@prisma/client";

    export const testTask = task({
      id: "test-task",
      run: async (payload: { message: string }) => {
        console.log("Trigger.dev task started:", payload.message);

        // Use a dedicated client for the task to avoid connection pool issues
        const prisma = new PrismaClient();
        try {
          const count = await prisma.project.count();
          console.log(`Database connection successful. Project count: ${count}`);
          return { success: true, projectCount: count };
        } catch (error) {
          console.error("Database connection failed:", error);
          throw error;
        } finally {
          await prisma.$disconnect();
        }
      },
    });

END OF trigger/test-task.ts snippet

### 3. Update `package.json`

Add the Trigger.dev dev script to your `package.json` scripts. Do not remove existing scripts.

START OF package.json snippet

    "scripts": {
      "dev": "next dev",
      "dev:trigger": "npx trigger.dev@latest dev",
      "build": "next build",
      "start": "next start",
      "lint": "next lint"
    }

END OF package.json snippet

### 4. Create Test Route `app/api/_test/trigger/route.ts`

Create a Route Handler that triggers the task. This is for verification only.

START OF route.ts snippet

    import { NextResponse } from "next/server";
    import { tasks } from "@trigger.dev/sdk/v3";
    import type { testTask } from "@/trigger/test-task";

    export async function GET() {
      try {
        const handle = await tasks.trigger<typeof testTask>("test-task", {
          message: "Hello from Next.js",
        });
        return NextResponse.json({ success: true, handle });
      } catch (error) {
        return NextResponse.json({ success: false, error }, { status: 500 });
      }
    }

END OF route.ts snippet
