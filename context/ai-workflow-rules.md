# AI Workflow Rules

## Approach

Build Systema incrementally using a spec-driven workflow. The approved context files define what to build, how to build it, and the current state of progress:

- `project-overview.md` — what the product does and the success criteria.
- `architecture.md` — stack, system boundaries, storage model, auth model, and invariants.
- `ui-context.md` — visual language, tokens, layout patterns, and interaction states.
- `code-standards.md` — TypeScript, Next.js, styling, API, data, and file organization rules.

Always implement against these specs. Do not infer or invent behavior from scratch. Code is a verified artifact of the specification, not the primary source of truth.

## Scoping Rules

- Work on one feature unit or subsystem at a time. A feature unit is a coherent slice of approved scope from `project-overview.md`.
- Prefer small, verifiable increments over large speculative changes.
- Do not combine unrelated system boundaries in a single implementation step. The boundaries in `architecture.md` (`app/`, `app/api/`, `actions/`, `components/`, `hooks/`, `lib/`, `lib/server/`, `trigger/`, `prisma/`, `types/`) define what counts as unrelated.
- Before starting a unit, identify its objective, the requirements it satisfies, the boundaries it touches, its dependencies, and the success criteria from `project-overview.md` that will verify it.

## When To Split Work

Split an implementation step if it combines:

- UI changes and background task changes (for example, building the canvas node editor and the Trigger.dev graph-generation task in one step).
- Real-time canvas state (Liveblocks) and database persistence (Prisma) that require distinct verification.
- Multiple unrelated API routes or Server Actions.
- Behavior that is not clearly defined in the context files.
- Changes whose combined scope makes reliable end-to-end verification difficult.

If a change cannot be verified end to end quickly using the checklist in "Before Moving To The Next Unit," the scope is too broad — split it.

## Handling Missing Requirements

- Do not invent product behavior that is not defined in the context files.
- If a requirement is ambiguous, resolve it in the relevant context file before implementing. Identify which file should own the decision (`project-overview.md` for product scope, `architecture.md` for structure and invariants, `ui-context.md` for visual rules, `code-standards.md` for implementation conventions).
- If a requirement is missing, add it as an open question in `progress-tracker.md` before continuing, and explain why the decision affects implementation.
- For low-impact implementation details that do not change product behavior, architecture, security, or approved conventions, use reasonable judgment within `code-standards.md`.

## Protected Foundation Components

Do not modify generated or foundation components unless a task explicitly requires it and you have approval.

Protected:

- `components/ui/*` — shadcn/ui primitives. Keep them default and reusable. Implement project-specific styling, layout, and feature logic in app-level components and composition, not by editing these files.
- `prisma/migrations/*` — generated by Prisma. Do not hand-edit; create a new migration instead.
- `lib/server/*` — server-only modules guarded by `server-only`. Changes here can break `architecture.md` invariant #5 (secrets must not reach client bundles).
- Third-party library internals — never modify `node_modules` or vendor internals.

Sensitive (require approval before structural changes):

- `lib/db.ts` — the Prisma singleton. Adding models or changing the connection setup affects the whole application.

**Canvas Layout & Drag-and-Drop (Critical)**
Do not modify the CSS layout chain (`h-full`, `calc(100dvh - 3.5rem)`) or the drag-and-drop event handlers in `components/editor/canvas/canvas.tsx` and `components/editor/editor-shell.tsx` unless explicitly instructed. This area is highly fragile. Any change that causes the React Flow parent container to lose its explicit height will make all nodes invisible, which requires manual browser debugging to fix. Always verify using Playwright MCP that the `.react-flow` container has a non-zero height after any layout change.

Not protected:

- Route pages, including Clerk sign-in and sign-out pages, are ordinary app-level pages. They are governed by `code-standards.md`, not this list.

Only modify protected files when a task explicitly requires it, and explain the reason, likely impact, and alternatives before proceeding.

## Keeping Docs In Sync

Update the relevant context file whenever an approved implementation decision changes:

- System architecture, boundaries, or invariants — `architecture.md`.
- Storage model or persistence decisions — `architecture.md`.
- UI tokens, layout patterns, or interaction states — `ui-context.md`.
- Code conventions or implementation standards — `code-standards.md`.
- Feature scope or approved product behavior — `project-overview.md`.

Keep `progress-tracker.md` accurate. Use these statuses: **Not started**, **In progress**, **Blocked**, **Done**. A unit is **Done** only when verification evidence is recorded against it. Progress state must reflect the actual state of the implementation, not the intended state. Never mark work as done because code has been written. Never claim a check passed unless its result was observed.

If `progress-tracker.md` does not exist yet, create it on first use with a minimal structure: current unit, status per unit, blockers, and open questions.

## Before Moving To The Next Unit

1. The current unit works end to end within its defined scope.
2. No invariant defined in `architecture.md` was violated.
3. `progress-tracker.md` reflects the completed work, with verification evidence recorded.
4. `npm run build` passes.
5. `npx tsc --noEmit` passes.
6. `npm run lint` passes, or introduces no new errors attributable to the current unit.
7. Manual verification of the unit's success criteria from `project-overview.md` is recorded in `progress-tracker.md`.

If a check fails:

- Investigate whether the failure was introduced by the current changes or existed beforehand.
- Fix issues caused by the current changes within the approved scope.
- Report pre-existing failures accurately. Do not disable checks, weaken the build, or change unrelated code to obtain a passing result.
- If a required check cannot be completed, report the limitation instead of declaring the unit fully verified.
